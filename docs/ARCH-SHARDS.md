# Солнечные системы на отдельных серверах: как и когда

Короткий ответ: **сможем**, и архитектура к этому готова больше, чем кажется.
Но «сервер на каждую систему» — не первый шаг. Правильный порядок: сначала
**шардинг по системе**, потом — вынос самой горячей.

## Что уже помогает

| Что есть | Почему важно для шардинга |
|---|---|
| В SQL у тел и агентов есть `system_id` | состояние уже разделено по системам |
| `SystemRuntime` в клиенте | система — изолированный инстанс, а не глобальная сцена |
| Каталог генерируется из БД | новый сервер поднимается из данных, без правок кода |
| `presence.json` хранит `system` игрока | видно, кто в какой системе |
| `race_schedule` считается от фиксированной эпохи | заезды не зависят от конкретного процесса |
| API stateless (токен в заголовке) | любой сервер может обслужить любой запрос |

## Что мешает прямо сейчас

| Проблема | Следствие |
|---|---|
| Состояние в JSON-файлах (`users.json`, `presence.json`) | два сервера не могут писать в один файл без гонок |
| Нет маршрутизации по системе | запрос игрока не знает, какой сервер его система |
| Перелёт между системами (Врата) | нужен «перехват» состояния при передаче |
| Общие рынок/чат/казино | они либо центральные, либо шардируются отдельно |
| Один PHP-процесс на всё | нет очереди событий для межсерверных сообщений |

## Три этапа

### Этап 1. Разделение состояния (сейчас — 1 сервер)

- Перенести `users.json` в SQLite/MySQL: транзакции вместо «перезаписать файл».
- Ввести `system_id` в ключевые записи: корабли, события, рынок по системам.
- Считать **нагрузку по системам** (уже есть `api?action=systems_load`):
  онлайн, тики, бои, заезды.

**Приёмка:** таблица «система → онлайн → тиков/с → размер состояния», обновляется раз в минуту.

### Этап 2. Шардинг по системе (2–3 сервера)

```
клиент → gateway (маршрутизация) → шард "sol"  (своя БД, свой тик)
                                 → шард "war"  (своя БД, свой тик)
                                 → общий слой: аккаунты, чат, рынок, казино
```

- **Gateway** знает карту `system_id → shard` (маленький JSON-конфиг).
- Каждый шард держит только свои тела, корабли, события, тики.
- **Перелёт между системами**: клиент получает `handoff`-токен, шард A
  фиксирует состояние и отдаёт шарду B; при ошибке — откат к A.
- Общие сервисы (аккаунт, чат, казино) остаются центральными: они не зависят
  от того, где находится корабль.

**Приёмка:** два шарда подняты, игрок в `sol` не влияет на FPS тика в `war`;
перелёт туда-обратно без потери кредитов и груза.

### Этап 3. «Горячую» систему — на отдельный сервер

Порог, после которого выносим:

| Метрика | Порог |
|---|---|
| Онлайн в системе | **> 40 %** от всех онлайн |
| Тик системы | **> 30 мс** на кадр при 20 Гц |
| Бои/события | **> 50 %** всех событий |
| Рост состояния | **> 100 МБ** за сутки |

Порядок выноса:
1. Снять метрики за неделю (этап 1 уже даёт цифры).
2. Поднять шард, переключить карту, прогнать перелёты.
3. Оставить остальные системы на общем слое — «не каждая».

## Что важно не сломать

| Правило | Почему |
|---|---|
| Одна физика | `motion-core` уже один; шард не должен вводить свою формулу |
| Один каталог | `system_id` из БД, а не из конфига сервера |
| Время от эпохи | иначе у шардов разные заезды и орбиты |
| Идемпотентность приказов | при handoff приказ не должен выполниться дважды |
| Наблюдаемость | без метрик «горячую систему» не выбрать |

## Честно о сроках и цене

| Этап | Что нужно | Оценка |
|---|---|---|
| 1. Состояние в SQL + метрики | код + миграция | 2–3 недели |
| 2. Шардинг + gateway + handoff | 2 сервера, конфиг, тесты | 4–6 недель |
| 3. Вынос горячей системы | по метрикам | 1–2 недели |

То есть «каждая система на своём сервере» — **не завтра**, но вполне реально
после этапа 1. Начинать надо не с серверов, а с **переноса состояния в БД и
метрик по системам** — иначе непонятно, что именно выносить.
